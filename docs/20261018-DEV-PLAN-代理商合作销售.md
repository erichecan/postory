## 零、关键背景核对（这步决定了下面怎么设计，不是我凭空加的范围）

现有系统里有几个容易和"代理商"概念混淆、但其实完全不是一回事的东西，已逐一核对清楚：

| 名字 | 实际是什么 | 和这次的关系 |
| :-- | :-- | :-- |
| `src/app/(agency)/*`（my-brand / my-campaign / calendar / dashboard） | 单个已登录商家自己的品牌管理视角，"agency"只是文案口吻（"你负责客户，我们是你的代运营"），不是多租户 | **可复用**：三节"流程演示"要看的月度计划/内容条目/campaign 结构，这里已经有现成数据结构 |
| `src/app/demo/my-brand`、`/demo/my-campaign`、`/demo/dashboard` | 上面那套页面的免登录只读镜像，数据来自 `src/lib/agency/demo.ts`（虚构门店 Sophie Chen Beauty Studio） | **直接复用**：这基本就是三节要的"流程演示"骨架，不需要重新做一套 |
| `src/app/demo/[industry]/*` + `src/lib/demo/*`（trial-protection / turnstile / render / DemoTrialGeneration） | 匿名访客自助体验：上传照片→AI 生成一张图，带防刷（Turnstile + IP/手机号哈希限额），单次、即时、不留档 | **部分复用**：媒体上传、渲染管线、防刷能力可以借；但身份模型不同（这次是代理商实名提交、要持久保留到人工交付、之后能转付费），不往这套表里塞 |
| `EndCustomer` | 商家自己的顾客名单（营销日历模块用来发生日祝福/召回短信），字段是 name/email/phone/birthday | **无关**，只是中文名字撞车，这次的"代理商的客户"不用这个模型 |
| `CustomerPlan`（`billing: STRIPE / OFFLINE`）、`CreditGrant`、`CreditTxn` | 现有按用户的额度/计费账本，已经有线下定价（`OFFLINE`）、按单元额度扣费（`GrantUnit: CREDIT / VIDEO`）的能力 | **直接复用**：代理商客户的额度和计费记在这套账本上，不新建一套平行的计费系统 |

## 一、这个模块是什么

给"营销个人/代理商"一条销售路径：代理商在 `/partners` 看懂合作方式 → 为一个真实客户提交免费试做（30 天计划 + 3 张图）→ 查看结果 → 确认转为预付费合作 → 代理商后台能看自己名下所有客户的额度和交付状态。试做阶段客户还没有自己的账号；一旦转付费，按你的决定（见需求原话存档第四条）为这个客户单独开一个"一人一工作室"账号，代理商对这个账号拥有操作权限，但数据归属仍然是这个客户自己的。

## 二、模块拆解

### 2.1 数据层（schema 变更）

**新表（全部 `Partner` 前缀，和现有 `(agency)`/`EndCustomer` 命名区分开）：**

- `PartnerTrialRequest`：试做申请主表
  `id, agencyUserId?(若代理商已登录则记录,允许匿名代理商先不登录提交), agencyName, agencyContact, clientBrandName, industry, country, productOrService, targetAudience, highlightNotes, platforms(String[]), websiteUrl?, socialHandles(Json?), languagePreference, viewToken(唯一,专属查看链接), status(SUBMITTED/IN_PROGRESS/DELIVERED/CONVERTED), convertedUserId?(转付费后指向新建的真实User), createdAt, deliveredAt?`
- `PartnerTrialAsset`：试做阶段的图片（对应"3 张不同图片"）
  `id, trialRequestId, storageKey, caption, platformVariants(Json: [{platform, exportedUrl}]), revisionCount Int @default(0), createdAt`
- `PartnerTrialPlanItem`：试做阶段展示的 30 天计划条目
  `id, trialRequestId, date, theme, platform, note`
- `PartnerTrialFeedback`：试做结果的反馈
  `id, trialRequestId, category(风格/内容准确性/修改意见), content, createdAt`
- `AgencyAccess`：代理商对某个客户账号的操作授权（解决存档第六条里留的"访问权限"遗留问题）
  `id, agencyUserId, clientUserId, createdAt`，`@@unique([agencyUserId, clientUserId])`

**现有表字段新增：**

- `Design` 新增 `revisionCount Int @default(0)`：对应你的决定 1——颜色/文字/构图微调原地累加这个字段，到 2 之后第 3 次编辑强制新建一条 `Design`（新扣一次图片额度），不是在原记录上无限原地改。
- `GenerationMode` 新增枚举值 `VIDEO`。
- `Generation` 新增 `durationSeconds Int?`：对应你的决定 2——生成视频时校验 ≤12 秒，超过走单独计费路径。
- `ChargeKind` 新增 `VIDEO_STANDARD`、`VIDEO_OVERAGE`：月度 2 个 12 秒视频额度内用 `VIDEO_STANDARD`，超出数量或超出时长的视频用 `VIDEO_OVERAGE`，具体单价你还没定，先建好凭证种类，单价字段留空不阻塞开发。

**不新增、直接复用的：**`CustomerPlan.billing = OFFLINE` 承载代理商客户的线下定价；`Design.platforms` 数组本身就是"一张图多平台不重复扣额度"的实现方式，不需要额外建关联表。

### 2.2 路由清单

公开（不需要登录）：
- `GET /partners` — 合作介绍页（主按钮"免费试做 3 张图片"，次按钮跳到流程演示）
- `GET /partners/trial` — 试做申请表单
- `POST /api/partners/trial` — 提交申请，返回专属查看链接
- `GET /partners/trial/[token]` — 专属查看链接：资料状态/补充资料/查看 30 天计划+3 张图+各平台版本/反馈入口/转付费入口
- `POST /api/partners/trial/[token]/feedback` — 提交反馈

复用现有、增量调整：
- `GET /demo/my-brand`、`/demo/my-campaign`、`/demo/dashboard` — 三节"流程演示"直接用这几个已有页面，只在合作页"查看合作流程"按钮上加跳转和分享封面（标题/摘要/封面图），不新建页面

代理商登录后（要求 session.userId 在 `AgencyAccess.agencyUserId` 里至少有一条记录）：
- `GET /partners/clients` — 客户汇总：客户数、各客户平台、产出数量、交付状态、月报入口
- `GET /partners/clients/[clientUserId]` — 以该客户身份查看/操作其账号（复用现有 my-brand/my-campaign/calendar/create 页面，鉴权规则在 2.3 里改）

后台（`/admin` 下新增，人工核账用）：
- 试做转付费确认动作：核实线下预付款到账后，创建客户 `User`（独立账号）+ `CustomerPlan(billing=OFFLINE)` + `AgencyAccess` 记录，把 `PartnerTrialRequest.status` 置为 `CONVERTED`

### 2.3 鉴权改动

现有所有"这是不是我的资源"的检查，都是 `session.userId === resource.ownerId` 的直接比较（`BrandProfile`/`Design`/`CalendarSlot`/`SocialAccount` 等）。这次要在这些检查上加一层"或者 `AgencyAccess` 里有一条 `(agencyUserId=session.userId, clientUserId=resource.ownerId)`"的放行条件。改动点分散在多个现有 DAL 文件里（`src/lib/db/profiles.ts`、`src/lib/db/social.ts` 等），这是本轮风险最高的一块，verify.sh 里会对每条相关路由单独做越权探针。

## 三、风险点

1. **跨账号访问权限是全新的攻击面**：以前系统里没有"A 能合法操作 B 的数据"这种场景，这次要在多个文件里补放行条件，漏改一处就是越权漏洞。verify.sh 逐条探针覆盖（见附录 A）。
2. **命名撞车但语义不同**：现有 `(agency)` 路由组、`EndCustomer` 模型，和这次的"代理商"字面撞车但完全是两回事，已经在零节核对清楚，这次新概念统一加 `Partner` 前缀和 `/partners` 路径，避免代码里出现两个"agency"混着用。
3. **复用判断（按大改要求评估）**——**已确认**：三节流程演示直接复用现有 `/demo/my-brand` 等页面，不新建；四节试做复用现有防刷/渲染基础设施，但状态模型新建（`PartnerTrialRequest` 系列），不往 `DemoTrialGeneration` 里塞。（2026-10-18 用户确认）
4. **试做名额"按客户限 1 次"的判重字段未定**：现有表单只有品牌名/联系方式，先用 `clientBrandName + agencyContact(联系方式)` 组合判重，如果同一个客户换了联系方式重复申请会漏判，这个我先用合理默认值处理，不是你明确说的规则。
5. **转付费流程**——**已确认**：PoStory 人工在 `/admin` 核实线下预付款到账后才创建客户账号，不是代理商自己点按钮立即生效。（2026-10-18 用户确认）
6. **平台费与计费细节（你决定里的第 3、8 条）仍未定**：本轮"计费说明"页面的具体数字和细项文案先不做，用"按客户定制报价，联系确认"代替，不影响上面所有核心流程的开发；等你想清楚了再补这页文案，不阻塞本轮。
7. **分页/N+1**：代理商客户汇总页按客户数分页查询，不在循环里逐个查 `CustomerPlan`/`CreditGrant`。

## 附录 A：技术验收标准（`scripts/verify.sh` 新增项）

- `npx tsc --noEmit`、`npm run build`、`npx prisma migrate status` 照常通过
- 路由探针：`/partners`、`/partners/trial`、`/partners/trial/[存在的token]`（200）、`/partners/trial/[随机token]`（404）
- 越权探针：
  - 代理商 A 访问代理商 B 名下客户的 `/partners/clients/[clientUserId]` → 403
  - 没有任何 `AgencyAccess` 记录的普通登录用户访问任意 `clientUserId` → 403
  - 未登录访问 `/partners/clients` → 302
- 修改次数探针：对同一个 `Design` 编辑 3 次，断言第 3 次产生新的 `Design` 记录并扣了新的 `CreditTxn`（不是原地累加 `revisionCount` 到 3 还不新建）
- 视频时长探针：提交 `durationSeconds > 12` 的生成请求，断言计费路径走 `VIDEO_OVERAGE`
- 多平台不重复扣费探针：同一 `Design.platforms` 增加一个平台，断言没有产生新的 `CreditTxn(kind=DEBIT)` 记录
- 试做判重探针：同一 `clientBrandName + agencyContact` 组合重复提交，断言第二次被拒绝或标记重复
