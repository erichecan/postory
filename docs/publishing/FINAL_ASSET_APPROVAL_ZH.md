# PoStory 最终图片审核与发布安全门禁（2026-11-21）

> PoStory 是 Done-for-You 社媒代运营；这是一套**内部交付约束**，不要求客户操作复杂设计软件。

## 必须依次满足的条件

1. PoStory 在目标环境完成 PNG/JPEG/WebP 的最终渲染或接收实际导出的图片文件。
2. 服务器完整解码该文件，核实文件类型、尺寸和大小，然后记录 SHA-256。无法解码、超限、非图片文件必须拒绝。
3. 中文/日文/英文文字叠加：运行在含 Liberation、DejaVu、Noto CJK 的生产镜像中，生成 SVG 前检查字形覆盖。**仅有字形覆盖并不能保证最终布局美观、文字没有挡住食物。**
4. 客户审核的必须是**服务器真实存储、将用于发布的最终图片**，以及该图片对应的完整社媒正文；客户明确批准。
5. 批准时分别记录图片与正文 SHA-256，以及批准时间。之后编辑或重做图片，必须重新走审核。
6. 最终导出图使用不可覆盖的随机存储键（本地文件独占新建，GCS 对象创建时 ifGenerationMatch=0）。
7. 调用 Ayrshare 排期前，重新读取同一存储对象并核对图片哈希、正文哈希及批准状态。只允许使用该**同一个存储 URL**，禁止在发布时再次生成图片。
8. FB/IG 等社媒仅接收已确认图片的 URL 和已确认文案。任何检查失败一律阻止发布；重复点击不会再次排期同一条已认领的餐饮内容。
9. WhatsApp 没有明确回复不能视为批准；24 小时超时会结束等待，不再自动发布。

## 现有两种交付路径

- **/editor 设计排期：** 保存设计 → 生成服务器最终预览 → 人工查看该图与正文 → 勾选明确确认 → 服务器记录图片与文案哈希 → 提交排期前再验哈希。
- **餐饮代运营 /restaurant：** PoStory 工作人员上传实际图片 → 服务器保存并验证 → 客户在原有审核链接审图、审文案 → 批准时锁定图文哈希 → 管理员排期前重新校验 → Ayrshare 直接引用原始已批准文件。

这两条路径之外的服务接入同一安全原则前，不能宣称完成了自动审核或安全发布。对于原来已经通过但没有哈希记录的历史内容，必须重新取得明确审核，不静默补签或自动放行。

## 自动质量检测与人工验收的边界

可自动检测：字体文件及常用字符覆盖、图片解码、类型/大小/尺寸、文件哈希变化、正文变化、批准状态、权限、重复排期。

不能可靠地只靠字体覆盖或像素统计检测：视觉层级错误、词句含义错误、字体过小、文字遮挡、真实商品误描述及图片中所有“豆腐块”字形。对此必须显示最终服务器文件并进行人工视觉审核；不能把通过文件测试称作通过设计验收。

## 生产部署检查

GitHub PR 测试包含：Prisma 校验、Next 类型检查、最终文件哈希/拒绝测试、Noto CJK 英中日字形测试、Lint 和生产构建。Cloud Run 部署中在**最终运行镜像**内用 fontconfig 核查英/中/日字体，并在部署后对 Sakura 渲染接口做 JPEG 请求检查。

每次上线应抽查：寿司营销页 7 个创意是否正确显示文字；编辑器最终预览能否加载；改变正文是否要求重新确认；餐饮客户审核后是否锁定旧文件；未批准或篡改资源是否被阻止发布。

## 回退

代码回滚不会自动撤销已经由社媒平台接受的排期。若需要撤销已排期内容，必须通过社媒服务商接口处理；请勿通过恢复旧数据库来假装撤销发布。
