## 二、组件职责说明

| 组件 | 职责 | 备注 |
|---|---|---|
| Page/UI 层 | 商家/运营方两套界面,纯展示与表单交互 | shadcn/ui + Tailwind,不含业务逻辑 |
| Server Action | 处理表单提交,做输入校验、权限校验,调用业务逻辑层 | 优先于传统 REST API,减少手写路由 |
| Cron 端点 | `/api/cron/process-jobs`,Vercel Cron 每 1-2 分钟触发一次,推进未完成的 Submission 状态机 | 因为 Orshot/Ayrshare 都是异步 job 模型,需要有人轮询 |
| Webhook 端点 | 接收 Ayrshare(若可用)的发布状态回调,减少纯轮询的延迟 | 作为 Cron 轮询的补充,不作为唯一依赖(webhook 可能丢失) |
| 业务逻辑层(services） | 每个模块一个 service 文件,封装"提交内容""生成内容""发布内容"等完整业务动作,内部调用 Provider 适配层 + Prisma | 单元测试主要针对这一层 |
| Provider 适配层 | 把 Orshot / Ayrshare / LLM 各自的 API 细节封装成统一的内部接口(如 `render(templateId, data): Promise<AssetResult>`),业务逻辑层不直接感知第三方 SDK 细节 | 架构保险:换厂商只改这一层 |
| PostgreSQL | 存客户、模板、提交记录、渠道连接、审计日志 | Prisma 管理 migration |

## 三、核心数据流时序(以"商家提交一条内容并发布"为例)

1. 商家在 `/dashboard/submit/[templateId]` 填写简介 + 上传照片,提交
2. Server Action `createSubmission` 校验后写入 `Submission`(status=DRAFT),返回给前端
3. 同一个 Action 内立即调用 `generateContent(submissionId)`:
   a. 先调 LLM 适配层生成 caption + hashtags,写回 `Submission.captionText/hashtags`,status → `GENERATING_ASSET`
   b. 再调 Orshot 适配层 `render()`,传入 `templateId` + 商家的 Logo URL/文案字段,拿到图片 URL,写回 `Submission.generatedAssetUrl`,记录 `orshotCreditsUsed`
   c. 全部成功后 status → `PENDING_REVIEW`;任一步失败,status → `FAILED` 并记录 `errorMessage`,不重复计费(用 Idempotency-Key)
4. 商家在 `/dashboard/submissions/[id]` 看到预览图+文案,点"确认发布并选时间"
5. Server Action `schedulePublish` 调用 Ayrshare 适配层:
   - 若时间是"现在":调 `publish`
   - 若时间是"未来":调 `schedule`
   - 写回 `ayrsharePostId`,status → `SCHEDULED` 或 `PUBLISHED`
6. Cron 端点定期轮询 `SCHEDULED` 状态且已过发布时间但状态未更新的记录,调 Ayrshare 查状态,同步为 `PUBLISHED`/`FAILED`
7. 全程关键节点写 `AuditLog`

## 四、安全设计

1. **多租户隔离**:所有面向 Client 的查询,Server Action 内强制以当前登录 Client 的 `clientId` 作为 where 条件的一部分,不信任前端传来的 `clientId`
2. **敏感凭证存储**:`ConnectedChannel.ayrshareProfileKey` 属于高敏感字段,数据库层加密存储(应用层加解密,密钥放环境变量,不落库),日志系统禁止打印该字段
3. **鉴权分层**:
   - Admin 路由组:要求 `AdminUser` 会话,`OWNER`/`STAFF` 角色区分(渠道 Key 管理、客户额度调整仅 `OWNER`)
   - Client 路由组:要求 `Client` 会话
   - 两套会话互不通用,同一 Next.js 应用内用路由组(`app/(admin)`、`app/(client)`)+ 各自的 middleware 校验区分
4. **第三方 API Key 隔离**:`ORSHOT_API_KEY`、`AYRSHARE_API_KEY`、`LLM_API_KEY` 只存在于服务端环境变量,任何 Provider 适配层调用只能在 Server Action / Cron / Webhook 里执行,不允许被打包进客户端 bundle
5. **幂等性**:调用 Orshot/Ayrshare 的每个写操作都带 `Idempotency-Key`(用 `Submission.id` + 操作类型拼出稳定 key),避免 Cron 重试导致重复扣费/重复发布

## 五、扩展性与后续演进

- 当前用"数据库表 + Cron 轮询"模拟任务队列,是 MVP 阶段的务实选择,避免引入 Redis/BullMQ 增加运维复杂度;若未来任务量大到轮询延迟不可接受,可平滑替换为真正的队列,因为业务逻辑层已经和"怎么触发"解耦
- Provider 适配层的存在使得"换掉 Orshot 换成 Bannerbear"或"Ayrshare 换成自建 OAuth"这类调研结论过时后的迁移,只需要重写适配层文件,不影响 UI 和数据模型
- 模板字段映射(`Template.fieldSchema`)设计成 JSON 配置而不是硬编码,新增模板不需要发版
