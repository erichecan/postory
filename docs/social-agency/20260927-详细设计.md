# 详细设计:每个功能点

本文档对应 DEV-PLAN.md 第 3 节的 13 个模块,逐一给出:功能描述、前置条件、输入输出、核心逻辑、涉及的外部 API、数据模型改动、异常处理、权限校验点。

---

## M1 认证与账号

**功能描述**:两套独立登录体系——运营方(AdminUser)与商家客户(Client),互不通用。

**输入/输出**:邮箱 + 密码登录,返回会话(建议用 `next-auth` 的 Credentials Provider,分别配置两个 provider 实例或用统一 provider + role 字段区分)。

**核心逻辑**:
```
login(email, password, expectedRole):
  user = 按 expectedRole 查 AdminUser 或 Client 表
  if !user or !verifyPassword(password, user.passwordHash):
    抛 401
  写会话 cookie,包含 { id, role, clientId? }
```

**异常处理**:登录失败统一返回"邮箱或密码错误",不区分"邮箱不存在"与"密码错"(防枚举)。

**权限校验点**:所有 `app/(admin)/*` 路由的 `middleware.ts` 校验 `role === 'admin'`;所有 `app/(client)/*` 路由校验 `role === 'client'`。这是 verify.sh 鉴权探针的直接对象。

## M2 商家客户档案

**功能描述**:运营方创建商家账号(MVP 阶段不开放商家自助注册,由运营方在后台手动开户,因为涉及线下签约/收费);商家登录后可以编辑自己的 Logo、品牌关键词、联系方式。

**输入**:`businessName`、`logoFile`(上传)、`toneKeywords: string[]`。

**核心逻辑**:
```
createClient(businessName, contactEmail):
  生成随机初始密码,通过邮件发给商家(或运营方手动告知)
  写入 Client 表,status = ACTIVE
  记 AuditLog(actorType='admin', action='client.create')

updateClientProfile(clientId, patch):
  校验 clientId === 当前会话 clientId(防越权)
  Logo 上传走对象存储(S3/Cloudflare R2,待确认,见假设清单新增项),写 logoUrl
```

**数据模型改动**:`Client` 表增删改。

**异常处理**:Logo 上传失败要给出明确错误,不允许留一个"损坏的 logoUrl"进数据库。

## M3 社交渠道连接

**功能描述**:商家在 `/dashboard/connect` 页面看到 Ayrshare 支持的平台列表,点"连接 Instagram"等按钮,系统生成一个 Ayrshare OAuth 授权链接,商家跳转过去自己完成授权,回跳后系统更新连接状态。

**前置条件**:该商家在 Ayrshare 侧已有一个 Profile(首次连接任意平台前,先调 Ayrshare 创建 Profile 的接口,拿到 `profileKey` 存入 `ConnectedChannel`/或单独的 `AyrshareProfile` 表)。

**核心逻辑**:
```
ensureAyrshareProfile(clientId):
  if Client 已有 profileKey: return 现有的
  调 Ayrshare POST /profiles,标题用 businessName
  存 profileKey 到 client 关联表(加密)
  return profileKey

getConnectLink(clientId, platform):
  profileKey = ensureAyrshareProfile(clientId)
  调 Ayrshare API,带 Profile-Key header,请求生成该 platform 的授权链接
  返回链接给前端,前端新开窗口跳转

syncChannelStatus(clientId):
  调 Ayrshare GET /profiles/social/accounts(带该客户的 Profile-Key)
  按返回结果更新 ConnectedChannel.connected / accountHandle / needsReconnect
```

**涉及的外部 API**:Ayrshare `POST /profiles`(创建)、连接链接生成接口、账号状态查询接口。

**异常处理**:Ayrshare 侧返回"授权已过期需要重新连接"时,把 `needsReconnect` 置 true,前端在渠道列表上高亮提示,不是静默失败。

**权限校验点**:`getConnectLink` 必须校验请求方是该 `clientId` 本人或运营方代操作(运营方代客户连接的场景需要单独审计记录,因为涉及经手客户账号权限)。

## M4 模板库(运营方维护)

**功能描述**:运营方去 Orshot 官网/Studio 挑模板,拿到 `orshotTemplateId` 后,在 `/admin/templates` 录入:模板名称、缩略图、行业分类、`fieldSchema`(这个模板暴露给商家填写的字段清单)。

**核心逻辑**:
```
createTemplate(orshotTemplateId, name, category, thumbnailUrl, fieldSchema):
  fieldSchema 示例:
    [
      { paramId: "title", label: "标题", type: "text", maxLength: 40, required: true },
      { paramId: "logo", label: "Logo", type: "image", source: "client.logoUrl" },  // 自动带入商家档案的 Logo,不需要商家重复填
      { paramId: "subtitle", label: "副标题", type: "ai_generated" }  // 由 AI 根据 briefText 生成,不需要商家手填
    ]
  写入 Template 表,isActive = true
```

**关键设计**:`fieldSchema` 里区分三种字段来源——`text`(商家手填)、`source: client.xxx`(自动带入商家档案数据,比如 Logo)、`ai_generated`(由 M6 的 AI 文案模块生成后填入)。这样商家真正要手填的字段可以压到最少(通常只有一句话简介),其余全自动拼装。

**异常处理**:录入时应有一个"测试渲染"按钮,用假数据调一次 Orshot render,确认 `fieldSchema` 里的 `paramId` 真的对应模板里存在的参数名,避免录错字段名导致商家提交后才报错。

## M5 内容提交(商家客户用)【2026-09-27 修订,替换了原"一段话 + AI 拆解"设计】

**功能描述**:商家从运营方筛选过的模板库里选一个,进入模板详情页,**按 `Template.fieldSchema` 逐字段填**(不是写一段话),边填边看预览图更新,确认后提交。原话见 `docs/20260927-social-agency-需求原话.md`"M5 内容提交流程澄清"。

**输入**:`templateId`、`fieldValues`(`Record<paramId, string>`,键来自该模板 `fieldSchema` 里 `type: 'text'`/`'image'` 的字段;`type: 'ai_generated'` 的字段不在这一步填)、`targetPlatforms`(勾选要发到哪些已连接平台)。

**预览机制**:详情页填字段时,停顿约 1.5-2 秒(防抖)后,前端拿当前 `fieldValues` 调一次 `renderTemplate`(跟 M7 最终出图是同一个 provider 函数,保证预览和实际发布效果一致),展示返回的图片 URL。这是刻意选的技术方案(比较过自建防抖表单 / 自建即时表单 / 直接嵌入 Orshot Embed 设计器三种做法,取舍见 DEV-PLAN.md 9.1 节)——**每次防抖触发的预览调用都会真的消耗 1 个 Orshot credit**,不是免费模拟,前端要对此保守(合理防抖间隔,不要每个按键都触发)。

**核心逻辑**:
```
previewField(templateId, fieldValues):
  // 详情页防抖触发,不落库,只是临时调用 renderTemplate 展示效果
  调 renderTemplate({ templateId: template.orshotTemplateId, modifications: fieldValues })
  返回图片 URL 给前端

createSubmission(clientId, templateId, fieldValues, targetPlatforms):
  校验 templateId 对应的模板 isActive
  校验 fieldValues 覆盖了 fieldSchema 里所有 required 字段
  校验 targetPlatforms 都在该 clientId 已连接的渠道范围内(不能选未连接的平台)
  写入 Submission(status = DRAFT, fieldValues, generatedAssetUrl = 最后一次预览图)
  异步触发 generateContent(submission.id)  // 见 M6(配文)/M7(正式出图),不阻塞本次请求返回
  返回 submissionId 给前端,前端跳转到 /dashboard/submissions/[id] 展示"生成中"
```

**数据模型改动**:`Submission.fieldValues` 存客户逐字段填的值(替代原来设想的"从 briefText 解析出字段值");不再需要 `briefText` 作为字段值来源,但保留一个可选的简短"配文提示"字段供 M6 生成社交配文时参考(不是用来拆解图片字段)。

**异常处理**:`targetPlatforms` 校验失败(选了未连接的平台)要在提交前的表单里就禁用勾选框,而不是提交后报错;预览调用失败(Orshot 报错/未配置)不能阻塞客户继续填表单,只在预览区展示"预览暂时不可用",允许照常提交(提交后 M7 会话真实渲染一次)。

## M6 AI 文案生成

**功能描述**:注意这里生成的是**发布到社交平台时帖子配文**(caption + hashtag),跟 M5/M7 生成的"图片本身的文字内容"是两回事——图片里的文字由客户在 M5 逐字段填,不经过 AI。M6 只根据商家的品牌信息,调 LLM 生成 caption 正文和一组 hashtag。

**核心逻辑**:
```
generateCaption(submission):
  prompt = 拼装(submission.fieldValues 里的文字字段、client.toneKeywords, client.businessName, 目标平台的字数/风格惯例)
  调 LLM API(见 lib/providers/llm.ts)
  解析返回,拆成 { captionText, hashtags: string[] }
  写回 Submission.captionText / hashtags
  status: DRAFT → GENERATING_ASSET
```

**异常处理**:LLM 返回内容为空或明显不合规(比如包含违禁词)时,不直接采用,回退到一个基于模板的保底文案(比如"{businessName} 有新动态啦!"),同时把 `errorMessage` 记一条警告,允许流程继续而不是整条卡死——这是一个降级策略,不是致命错误。

**Provider 适配层**:`lib/providers/llm.ts` 暴露 `generateCaption(input): Promise<{captionText, hashtags}>`,内部实现可替换供应商。

## M7 图片/视频生成

**功能描述**:调用 Orshot `render` 接口,把 `fieldSchema` 定义的各字段值(含 M6 生成的文案、商家 Logo、商家上传的照片)拼成 `modifications` 对象,渲染出成品图。

**核心逻辑**:
```
generateAsset(submission, template, client):
  modifications = {}
  for field in template.fieldSchema:
    if field.type == 'text': modifications[field.paramId] = submission.fieldValues[field.paramId]  // 客户在 M5 逐字段填的值,不再从 briefText 解析
    if field.source == 'client.logoUrl': modifications[field.paramId + '.imageUrl'] = client.logoUrl
    if field.type == 'ai_generated': modifications[field.paramId] = submission.captionText 的短版本(取标题句)

  调 Orshot POST /v1/studio/render:
    { templateId: template.orshotTemplateId, modifications, response: { type: 'url', format: 'png' } }
    带 Idempotency-Key = submission.id + ':render'

  成功: 写回 generatedAssetUrl,orshotCreditsUsed += 1(或按模板页数计),status → PENDING_REVIEW
  失败: status → FAILED,记录 errorMessage,不重试超过 3 次(与全局 CLAUDE.md"编译错误最多修 3 次"精神一致,这里是"外部调用失败最多自动重试 3 次")
```

**涉及的外部 API**:Orshot `POST https://api.orshot.com/v1/studio/render`。

**异常处理**:
- Orshot 返回 429(限流):按 `Retry-After` 退避重试
- Orshot credit 用尽:立即停止,给运营方发告警(见 M11),不能让商家提交的内容无限堆积在"生成中"状态
- 渲染成功但图片明显异常(比如尺寸为 0,Orshot 返回错误状态但 HTTP 200):做基本的响应体校验,不能只看 HTTP status code 就判定成功

## M8 预览与审核

**功能描述**:商家在 `/dashboard/submissions/[id]` 看到生成好的图 + 文案,可以选择"确认发布"或"重新生成"(消耗新的 credit)。MVP 阶段不支持修改文案/图片细节(客户不碰编辑器,这是产品边界)。

**核心逻辑**:
```
approveSubmission(submissionId, scheduledAt?):
  校验 status === PENDING_REVIEW
  调 M9 schedulePublish(submissionId, scheduledAt)

regenerate(submissionId):
  校验 status in [PENDING_REVIEW, FAILED]
  重新走一次 M6 + M7(会再消耗一次 credit,前端要明确提示"将消耗 1 个额度")
```

**权限校验点**:只有该 submission 所属的 `clientId` 或运营方可以 approve/regenerate。

## M9 排期与发布

**功能描述**:调用 Ayrshare 的 `schedule` 或 `publish` 接口,把生成的图 + 文案发到商家选定的目标平台。

**核心逻辑**:
```
schedulePublish(submission, scheduledAt):
  body = {
    post: submission.captionText + hashtags,
    mediaUrls: [submission.generatedAssetUrl],
    platforms: submission.targetPlatforms 映射成 Ayrshare 平台标识,
    profileKey: client 对应的 Ayrshare Profile-Key,
    scheduleDate: scheduledAt   // 不传则立即发布
  }
  调 Ayrshare POST /post,带 Idempotency-Key = submission.id + ':publish'
  成功: 写回 ayrsharePostId,status → (scheduledAt ? SCHEDULED : PUBLISHED)
  失败: status → FAILED,记录 errorMessage(区分 CHANNEL_NOT_CONNECTED / INSUFFICIENT_CREDITS 等 Ayrshare 错误码,展示对用户友好的提示)
```

**异常处理**:
- `CHANNEL_NOT_CONNECTED`:该平台连接过期或从未连接,提示商家去 M3 重新连接,而不是显示一个不可理解的报错码
- Ayrshare 侧限流(429):同 M7,退避重试

## M10 历史与状态跟踪

**功能描述**:商家查看自己名下所有 `Submission` 的列表(分页),按状态筛选。

**核心逻辑**:cursor-based 分页查询,`where: { clientId: currentClientId }`,不做全表扫描。

**风险点**:必须建索引 `@@index([clientId, createdAt])`,否则数据量大后列表查询会全表扫。

## M11 运营后台:客户与用量管理

**功能描述**:运营方查看每个客户当月消耗了多少 Orshot credit、连了几个 Ayrshare 渠道,可以给客户设 `creditLimit`(超过后新的提交会被拒绝并提示商家联系客服)。

**核心逻辑**:
```
checkCreditLimit(clientId):
  monthlyUsed = sum(Submission.orshotCreditsUsed where clientId, createdAt in 本月)
  if client.creditLimit != null and monthlyUsed >= client.creditLimit:
    拒绝新的 M5 提交,返回明确提示
```

**告警**:当运营方账号自己的 Orshot/Ayrshare 总账即将用尽(比如剩余 <10%),后台首页要有醒目提示,避免商家提交了内容却因为运营方自己的套餐见底而生成失败。

## M12 异步任务处理器

**功能描述**:Vercel Cron 每 1-2 分钟调用一次 `/api/cron/process-jobs`,做两件事:

1. 扫描 `status IN (GENERATING_CAPTION, GENERATING_ASSET)` 且 `updatedAt` 超过 5 分钟未更新的记录(说明上一次触发可能失败/超时),重新驱动一次流水线(利用 Idempotency-Key 保证不重复扣费)
2. 扫描 `status = SCHEDULED` 且 `scheduledAt` 已过去超过 10 分钟、但状态未变成 `PUBLISHED` 的记录,主动查一次 Ayrshare 的发布状态,同步结果

**异常处理**:单条记录处理失败不能影响本次 Cron 批次里其他记录的处理(逐条 try/catch,不整体回滚)。

## M13 审计日志

**功能描述**:所有关键写操作(创建客户、连接渠道、发布内容、修改额度)都记一条 `AuditLog`,运营方后台可查。

**核心逻辑**:统一封装 `logAudit(actorType, actorId, action, metadata, clientId?)`,在每个 Server Action 的关键分支里调用,不遗漏。
