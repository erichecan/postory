# PoStory Content Engine · 产品与技术决策（正式版 v1）

日期：2026-11-21  
状态：已确认产品原则；研发方案待逐阶段验收  
首个样板行业：寿司／餐饮  
角色定位：**Done-for-You 营销代运营**，不是对外销售通用设计 SaaS。

## 0. 决策摘要

1. **行业独立对外，底层共用**：不同客户从独立行业 URL 和行业专属页面进入；默认不展示其他行业能力。可以保留一个独立、非默认的行业总览页，承接官网／代理入口，但不强制每个客户从总览选行业。
2. **每个行业独立的营销选择**：通用目标分类仅供内部数据分析；每个行业的用户可见目标、案例、促销规则和模板库独立配置。不强迫所有行业套同样七个目的。
3. **Brand Profile 是首个正式交付价值**：首次收集店名、Logo、门店实景、商品照片、服务范围、价格／规则／品牌偏好，系统识别并提出品牌规范候选，由店主确认并锁定版本。后续工作复用、变更可追溯。
4. **真实素材优先**：默认采用确定性修图（裁剪、曝光、白平衡、压缩等），必要时用 AI 对局部背景优化；不虚构商品、菜品、施工结果、资质、评论或优惠条件。
5. **专业模板 + 图层 Renderer**：先确立设计规范和经审核的优质模板。背景／商品素材／Logo／文字／优惠事实分层保存与渲染。文字和尺寸变化优先只重渲染，不重新生图。
6. **手机壳只用于预览**：iPhone/Facebook UI 是固定前端组件。发布的媒体资产与平台预览独立，不能把“Facebook 手机截图”当作营销图片发布。平台 UI 随时可能变化，模拟预览不能宣称完全一致。
7. **促销先结构化，再出图文**：行业促销类型驱动动态表单；核实商品、期限、渠道、门槛、资格、排除条件与比较价格；海报仅展示必要承诺和重大限制，正文或详情完整展示，所有展示从同一份事实对象渲染。
8. **文案分层**：图片短标题、完整平台正文、CTA、完整促销规则分别生成和审核；不同平台使用不同长度与文案策略，严禁虚构事实。
9. **模板库可离线批处理，但需要质量门禁**：每日脚本可生产设计候选及中性素材，不可把大量未经审核的随机图片当模板发布。去重、检查构图和文字区域、人工抽检、版本化发布。
10. **客户批准后才发布**：邮件发送审核入口，身份验证与有效期、单条／整批审核、明确修改反馈、版本哈希和审核记录；内容发生重大修改则撤销批准。排期／发布状态、重试和审计必须清楚。
11. **成本可衡量**：监控每月生成式图片调用数、缓存命中、修图／模板渲染次数、失败率、人工审核时长、客户修改率，不凭猜测承诺降本比例。

## 1. 对外产品入口与品牌信任

### 1.1 URL 策略（拟定，不等于已上线）
- `/for/sushi`：寿司／日式餐饮专属落地页、行业案例和业务入口；
- `/for/nail`：美甲专属入口；
- `/for/roofing`：屋顶服务专属入口；
- `/for/accounting`：会计／报税入口；
- 未来扩展其他垂直行业；
- `/industries`：可选行业总览页，通常用于官网和代理商入口，**不应自动出现在每个行业客户的主要购买路径中**。

这些路径是待开发 URL 建议；正式链接应经过 SEO、现有路由和权限检查后确定。行业客户可从专属落地页进入对应营销流程，并携带受控的行业标识；服务端应复核并锁定可用规则，不能仅信任客户端提交的行业代码。

### 1.2 产品表达
- 对寿司客户：说“我们懂寿司店的午餐、菜单、回访和本地获客”，不在销售页列出屋顶／会计等行业。
- 对屋顶客户：突出工程实景、报价咨询、服务区域与可信度，不套餐饮语言。
- PoStory 可以有跨行业运营后台；前台体验与证据必须行业化。

## 2. 营销目的与促销能力

### 2.1 双层目标分类
- **内部共用分析**：获客、转化、复购／关系、客单价值、品牌认知、特定时段／季节。
- **行业专属显示**：每个行业自己定义 3–6 个优先目标、描述、可选促销类型、CTA、适用案例。
- 未确定目标时，先从经营问题诊断，不以虚构促销作为默认建议。
- 不同目标能够复用相同基础模板槽位，但展示的案例须真正解释“这类内容怎样支持该目标”。

### 2.2 行业示例（初稿，待访谈验证）
| 行业 | 优先目标 | 促销与合规重点 |
| --- | --- | --- |
| 寿司餐饮 | 午餐到店、新品菜品、回访、套餐、淡时段、地区知名度 | 套餐价格、参与菜品、堂食／自取／配送、日期和时段、会员资格、过敏与真实菜单 |
| 美甲／美容 | 新客预约、作品展示、老客回访、档期填充 | 服务项目、初次到店条件、适用时段、预约和取消政策、效果不得保证 |
| 屋顶／装修 | 获取报价、展示工程、地区信任、季节检查 | 服务范围、实际资质、报价条件、保修与工程照片授权，不默认价格折扣 |
| 会计／报税 | 预约咨询、专业信任、报税季、企业服务 | 服务资格和真实承诺、预约范围、隐私与敏感资料保护，不编造税务结果 |
| 健身 | 体验预约、课程推广、续费、档期 | 体验资格、时段、取消政策、不承诺健康结果 |

### 2.3 促销类型是独立领域对象
通用字段：`type`, `items`, `startAt`, `endAt`, `timezone`, `channels`, `eligibility`, `limitations`, `stackability`, `approvalStatus`；金额／原价／折扣／赠品／门槛为按类型条件字段。
- UI 按行业和类型分步提问，不把规则交给一个大文本框。
- 未填写关键限制不得宣称完整促销。
- 大幅优惠、价格对比、赠品等信息必须以真实事实为依据，并随适用市场做合规检查。
- 图片中的优惠标题、价格、日期、重大条件必须从同一促销事实对象映射；完整规则保留在正文／活动详情。
- 商家确认事实不等于平台自动批准发布，仍要经过内容审核。

## 3. Brand Profile（优先级 P0）

### 3.1 输入与产出
输入：准确店名、Logo、联系方式和地址／服务区域、语言、已存在的品牌色、店内实景、商品／项目照片、菜单／服务清单、价格和事实、客户授权的典型作品。

产出：**可审核的品牌规范资料**（品牌名称、行业、语言、logo 版本、候选配色、字体与语气、定位、禁用话术、照片使用规则、商品事实来源、场景素材集合、审批状态和版本号），并提供简短可视化的“你的网站／社媒将采用什么品牌风格”页面，增强服务价值感。

### 3.2 事实与推论边界
- `merchant_confirmed`：商家确认的事实，例如店名、菜单价格、实际营业时间。
- `extracted_candidate`：AI 或图像分析提议，例如品牌主色、照片类别、常见文案语气。
- `designer_selected`：PoStory 内部设计师确认的视觉规范。
- 未确认的属性不能自动作为促销事实发布；每项内容保留来源／确认时间和变更记录。
- 真实照片保留原图、优化图、许可与修改记录；不能在未取得许可情况下用于公开案例。

### 3.3 数据安全
- 服务端验证上传文件 MIME、尺寸和访问权限。
- 商家原始资产与其他客户强隔离；存储引用不暴露跨客户访问。
- Brand Profile 更新须显式批准；发布版本引用某个固定 Profile 版本，避免历史内容突然变更。

## 4. 内容生成与分层设计

```text
Industry-specific URL + approved Brand Profile
  → Business strategy / industry objective / promotion facts
  → Source asset intake (originals + metadata)
  → Deterministic enhancement by default; AI retouch only where necessary
  → Template matching by industry, purpose, crop, text length, brand rules
  → Copy drafting from verified facts + editing
  → Deterministic layer render (brand / real assets / typography / offer / CTA)
  → Media assets per aspect ratio (1:1, 4:5, 9:16 as appropriate)
  → Fixed platform preview frame (Facebook/Instagram/etc.; never exported as post image)
  → Merchant review by authenticated email link
  → Approved version lock → schedule → publish → report
```

### 4.1 素材处理等级
A. 通用非生成式：裁剪、适度校色、压缩、清晰度处理；可复用；保留原件。
B. 特定需求的 AI 局部编辑：去干扰背景、扩画布、重布景；需人工检查商品真实性。
C. 允许生成概念图／非纪实背景，但必须标明来源；不可冒充真实食物／门店／工程。

### 4.2 模板库
模板应保存结构化字段，而非仅保存成品 PNG：
`templateId`, `version`, `industryIds`, `objectiveIds`, `format`, `visualSlots`, `logoSafeArea`, `headlineMaxChars`, `offerFields`, `ctaStyle`, `requiredAssets`, `qualityStatus`, `license`。
初期先做好寿司行业的五种专业内容形式：真实食物摄影主视觉、单品重点推广、组合展示、明确活动规则的促销海报、真实门店品牌故事。每种至少有不同的版式变体，并进行手机尺寸可读性验收。

### 4.3 质量门禁
- 主体是否清晰、是否与营销目标相关；视觉吸引力、可读性、品牌一致性、事实准确性。
- 断字溢出、Logo 安全区、平台裁切、价格或日期冲突、虚构商品内容一律阻断自动批准。
- 自动评分只用于排序与筛查；初期每一套基础版式需要人工评审。
- 参考优秀设计的原则，不复制第三方广告作品或其商标。

### 4.4 文案与模板的分离
每条内容至少包含 `headlineOverlay`、`bodyCopy`、`cta`、`disclosure`（若有）、`verifiedClaims`、`locale`、`platform`。
文案生成应区分：真实产品细节、目标顾客场景、明确 CTA、经确认的优惠，不使用无根据的“最好”“保证”“仅剩几份”等表述。
更新纯文字应只触发文字重新排版；不是重新生成商品照片。

## 5. 预览、邮件批准与发布

- iPhone 和 Facebook 等平台 UI 为固定组件，绝不交给生图模型；内部预览与实际媒体导出两条产物分开。
- 每条内容版本关联 `brandProfileVersion`、`templateVersion`、`assetHashes`、`copyHash`、`offerVersion` 和 `renderHash`。
- 状态机：`draft` → `ready_for_review` → `approved` → `scheduled` → `published`；另有 `changes_requested`、`failed`、`cancelled`。
- 邮件优先发送每周／批量审核通知，特殊活动单独审核。邮件链接应验证身份、设置有效期与防重放，支持批准／要求修改。
- 审核人批准的是精确版本；更改图片、重要文案、价格或活动规则，必须重新批准。
- 发布通过有授权的平台通道，记录发布 ID、状态、失败重试与人工处理；禁止将“显示成功提示”视为发布成功。
- 代理商白标流程必须保持渠道隔离；按代理合同要求不直接联系代理客户的终端商家。

## 6. 成本与缓存策略

`Cost = (文本生成调用 × 单价) + (AI 图片调用 × 单价) + 存储和渲染成本 + 人工审核时间`。

优先优化：
- 相同原始照片只处理一次，按内容哈希和处理参数复用优化产物。
- 同一模板在不同比例下确定性布局；语言、价格、字体变更不触发生图。
- 图片／设计模板库离线批量生成并验证；生产环境匹配已验收模板。
- 允许用户要求重新生成，但展示原因并记录调用和成本。
- 每月观测生成图片调用/20条、无 AI 渲染比例、缓存命中、客户修改比例、审核周转时间以及实际失败率。

## 7. 与现有代码的关系（截至 2026-11-21 的核查）

已存在：
- `/store` 单一路由及五步流程，营销目的、门店资料、营销方式、商品资料、发布安排。
- `/api/marketing-calendar`：行业内容规则 + 营销目的规则，输出文本日历。
- `/api/marketing-calendar/image`：带已有缓存和真实商品照片输入的 AI 生图接口；即使商品照片存在，当前仍可能生成新图。
- 前端固定手机预览 UI，生成日历后可预览及编辑内容。
- `scripts/generate-daily-templates.ts` 已存在，但采用固定轮换的行业／主题生成模式；**不等于已上线的、经过质量审核的分层行业模板引擎**。
- `/nails` 有独立美甲工作区入口（含身份要求），需要与未来行业路由策略兼容。

尚未作为新方案核实实现：
- 行业专属销售入口与端到端专属内容引擎；
- Brand Profile 候选提取、审核和版本化持久化；
- 完整结构化促销对象及行业条件表单；
- 受控的分层图像渲染与高质量模板门禁；
- 完整的邮件审核→版本锁定→自动发布服务。

当前 `publishOrSchedule()` 仅设置界面提示，**不能视为真实自动发布**。当前 `generatePlan()` 默认针对多个帖子逐条请求图片生成，因此不能将缓存存在当作已解决生成成本问题。

## 8. 不在本轮范围

- 不改变用户对 PoStory 的 Done-for-You 服务合同或把它改为自助 SaaS。
- 不一次开发所有行业的完整运营功能。
- 不在缺乏授权的情况下调用生产 API key 或批量自动发布。
- 不直接生成或发布真实客户尚未确认的折扣、客户故事、实景工程或效果承诺。

## 9. 接受标准

第一个完整行业（寿司）应能在行业专属链接进入 → 建立并确认 Brand Profile → 上传真实素材 → 根据行业目标和结构化规则选模板 → 在固定手机预览中同时看到可发布媒体与平台文案 → 审核版本 → 可安全排期发布。上线前必须通过真实性审核、权限测试、移动端设计验收和端到端测试。
