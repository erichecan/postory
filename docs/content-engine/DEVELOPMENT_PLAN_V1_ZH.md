# PoStory Content Engine · 开发计划及验收清单 v1

制定：2026-11-21  
目标：以 **寿司／餐饮单行业** 做出有实际设计品质、可靠事实和审核能力的首个可交付闭环；基础模块可复用，行业对外独立。  
边界：**代码完成不代表已部署**；每个阶段按验收结果推进，默认不得自动合并／生产部署。

## 原则与顺序
P0 先解决定位、品牌资料和设计质量；P1 实现分层产出、行业促销；P2 做审核发布和成本控制；P3 复制其他行业。不要为了抢进度提前生成大量未审核的 AI 海报。已有 `/store` 运行逻辑在迁移期间应能回退。

## 第一个交付迭代：M0-1（当前开始执行）

当前 PR 应包含：
1. 独立的中文正式决策文档；
2. 本分期研发计划；
3. 类型化 `industryRegistry`（行业 key、用户可见目标、允许的促销类型和专属路径，寿司、屋顶作为差异验证样本）；
4. 类型化 `BrandProfileDraft`／事实来源和审核状态模型，作为下一步服务端存储契约；
5. 轻量脚本检查行业配置完整性／差异和 Brand Profile 基础约束。

本 PR 不做：
- 不修改生产 `/store`，不尝试完成 Brand Profile 数据库、上传或授权；
- 不宣称模板库、邮件审核、真发布已实现；
- 不合并和部署生产，直至审核确认。

**本迭代验收：**
- `npm run typecheck`（含 Next.js typegen）与目标脚本运行成功；
- Registry 返回餐饮与屋顶不相同的目标和促销清单；
- 行业入口独立，不以统一“什么都能做”作为销售页主文案；
- Brand Profile 型别明确“确认前不可当作事实发布”的界限；
- 当前已有营销日历 API 与操作不受更改。

## 第二个交付迭代：M0-2 与 M0-3

- 首先建立可独立分享的 `/for/sushi` 页面，后续内链进入受控行业流程（不贸然改变已有登录和权限）。
- 门店首次提交 Brand Profile 草稿，设计复核页与确认动作；服务端绑定商家 tenantID；存储使用现有上传服务能力，避免直接使用浏览器 localStorage 作为长期真实资产库。
- 完成至少三组验证：寿司店 / 屋顶服务的行业隔离；已确认/待确认字段隔离；多客户不共享图片访问权限。

## 第三个交付迭代：M0-5 + M1-1 + M1-2

以三种经过人工设计验收的寿司真实照片完成设计试验：
- A. 主推单品近景，最少字；
- B. 真实套餐组合图，真实价格与有效日期可选；
- C. 真实餐厅环境／服务，品牌故事；
再补充两种高级版式（知识轮播、重要活动），产出定稿。通过对比专业参考、手机尺寸视觉检查、排版溢出检查后，才能让 Renderer 进入客户交付流程。

## 发布与回滚门禁

任何线上更新必须具备：构建成功、视觉对比、旧流程回归测试、真实数据隔离测试、审核与权限验证、可回滚的部署镜像；由具备部署权限的环境执行上线并验证实际 Cloud Run 版本。此表不代表已经具备相应部署权限。

## 项目管理方法

- 一个工作项对应一个可验证 PR；优先提交安全、低耦合模块。
- 产品评审关注行业定位、客户价值和设计品质；技术评审关注事实边界、租户隔离、模板可复用、成本和真实发布的安全性。
- 每轮验收采用“演示证据 + 自动测试 + 人工确认”，不将页面能打开视为整个系统已完成。
