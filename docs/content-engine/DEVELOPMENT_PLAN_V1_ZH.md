# PoStory Content Engine · 开发计划及验收清单 v1

制定：2026-11-21  
目标：以 **寿司／餐饮单行业** 做出有实际设计品质、可靠事实和审核能力的首个可交付闭环；基础模块可复用，行业对外独立。  
边界：**代码完成不代表已部署**；每个阶段按验收结果推进，默认不得自动合并／生产部署。

## 原则与顺序
P0 先解决定位、品牌资料和设计质量；P1 实现分层产出、行业促销；P2 做审核发布和成本控制；P3 复制其他行业。不要为了抢进度提前生成大量未审核的 AI 海报。已有 `/store` 运行逻辑在迁移期间应能回退。

## 第一个交付迭代：M0-1（当前开始执行）

当前 PR 应包含：
1. 独立的中文正式决策文档；
2. 本分期研发计划；
3. 类型化 `industryRegistry`（行业 key、用户可见目标、允许的促销类型和专属路径，寿司、屋顶作为差异验证样本）；
4. 类型化 `BrandProfileDraft`／事实来源和审核状态模型，作为下一步服务端存储契约；
5. 轻量脚本检查行业配置完整性／差异和 Brand Profile 基础约束。

本 PR 不做：
- 不修改生产 `/store`，不尝试完成 Brand Profile 数据库、上传或授权；
- 不宣称模板库、邮件审核、真发布已实现；
- 不合并和部署生产，直至审核确认。

**本迭代验收：**
- `npm run typecheck`（含 Next.js typegen）与目标脚本运行成功；
- Registry 返回餐饮与屋顶不相同的目标和促销清单；
- 行业入口独立，不以统一“什么都能做”作为销售页主文案；
- Brand Profile 型别明确“确认前不可当作事实发布”的界限；
- 当前已有营销日历 API 与操作不受更改。

## 第二个交付迭代：M0-2 与 M0-3

- 首先建立可独立分享的 `/for/sushi` 页面，后续内链进入受控行业流程（不贸然改变已有登录和权限）。
- 门店首次提交 Brand Profile 草稿，设计复核页与确认动作；服务端绑定商家 tenantID；存储使用现有上传服务能力，避免直接使用浏览器 localStorage 作为长期真实资产库。
- 完成至少三组验证：寿司店 / 屋顶服务的行业隔离；已确认/待确认字段隔离；多客户不共享图片访问权限。

## 第三个交付迭代：M0-5 + M1-1 + M1-2

以三种经过人工设计验收的寿司真实照片完成设计试验：
- A. 主推单品近景，最少字；
- B. 真实套餐组合图，真实价格与有效日期可选；
- C. 真实餐厅环境／服务，品牌故事；
再补充两种高级版式（知识轮播、重要活动），产出定稿。通过对比专业参考、手机尺寸视觉检查、排版溢出检查后，才能让 Renderer 进入客户交付流程。

## 发布与回滚门禁

任何线上更新必须具备：构建成功、视觉对比、旧流程回归测试、真实数据隔离测试、审核与权限验证、可回滚的部署镜像；由具备部署权限的环境执行上线并验证实际 Cloud Run 版本。此表不代表已经具备相应部署权限。

## 项目管理方法

- 一个工作项对应一个可验证 PR；优先提交安全、低耦合模块。
- 产品评审关注行业定位、客户价值和设计品质；技术评审关注事实边界、租户隔离、模板可复用、成本和真实发布的安全性。
- 每轮验收采用“演示证据 + 自动测试 + 人工确认”，不将页面能打开视为整个系统已完成。


## M0-2 页面代码阶段（2026-11-21）
- 已加入独立寿司行业介绍路由：`/for/sushi`。聚焦寿司行业，不与美甲、屋顶、会计同页推介。
- 已加入 Brand Profile 首次录入与视觉预览：`/for/sushi/brand`，可录入店名、位置、品牌语气与色彩，上传 Logo、店内实景和商品图片，在本地显示预览与资料完整度。
- 该版本**仅为客户端交互及临时素材预览**：所选图片和字段未保存到服务器，刷新会丢失；“确认当前预览”只更新本地 UI，不创建正式批准版本。页面显著披露这一边界。
- 下一步必须实现经身份验证的真实品牌资产上传、租户隔离、Brand Profile 的候选提取/确认/版本化数据库存储，再按设计规范接入 Renderer。
- 尚未修改 `/store` 的生产业务流程、营销图片生成接口、真实审核与发布。


## M0-3 持久化开发切片（2026-11-21）

### 本次已写入开发分支
- 复用现有 PoStory 登录 Session，未登录只能本地预览，接口返回 401；所有写入要求同源校验。
- 新增 **ContentBrandProfile** 与 **ContentBrandAsset**，与旧的 `BrandProfile` 账号资料表隔离。首版暂按 `ownerId` 一账号一份寿司品牌档案，未来多门店必须升级为按客户/门店租户建档。
- 新增 Prisma 迁移 `20261121093000_content_brand_profiles`，部署前需执行迁移，未执行迁移时 API 无法正常操作。
- `GET/PUT /api/content-engine/brand`：读取当前账号唯一档案；只保存 `draft`，使用 `expectedRevision` 乐观锁防止多页覆盖；只可引用同账号素材；所有字段目前均为 `proposed`，保存不等于经过商家或设计师审核。
- `POST /api/content-engine/brand/assets`：仅认证用户上传 JPG/PNG/WebP，单张 6 MiB 内，签名与文件声明类型一致，保存到独立 `content-brand/{ownerId}/{assetId}` 私有对象存储，DB 记录归属、摘要与类型。
- `GET /api/content-engine/brand/assets/[id]`：通过 Session 和 DB 资产归属双重校验私有素材读取，不走公开缓存媒体通道。
- 前端 Brand Profile 可在登录后手动保存草稿，刷新自动读取与恢复。未登录明确提示“登录后保存”；未保存的本地对象 URL 不会自动提交。点击保存不会批准商业使用权限或触发发布。
- 存储中沿用现有 `STORAGE=local|gcs` 适配，**生产必须设置 GCS Bucket，不能假设 Cloud Run 本地磁盘可以持久化**。

### 上线前仍未完成的验收
1. 在测试 PostgreSQL 上真正运行 `prisma migrate deploy` 并验证反向兼容；CI 目前仅 TypeScript、ESLint、域规则与构建，不连接生产数据库。
2. 用两个真实测试账号检查图片跨账户访问：他人 GET 必须 404，PUT 引用他人素材必须 403，未登录 GET/PUT 必须 401。
3. 在 Cloud Run/GCS 测试环境上传 JPG/PNG/WebP，验证容量限制、存储、恢复与图片显示、网络中断行为；当前代码检查不等于线上测试。
4. 生产前加严格图片解码与像素尺寸限制、资产过期/删除策略、重复上传清理、访问频率限制；目前已做类型签名与字节上限，但还不是全面的素材安全管线。
5. 正式的 Brand Profile 审批状态、变更历史和审核权限，必须由下一迭代开发；目前版本号只用于草稿更新冲突防护，不能宣称已提供历史版本回滚。
6. 代理商多客户的租户级权限模型需要在正式客户上线前完成，**首版 ownerId 模式不能用于多门店/多客户代运营生产**。

### 操作门禁
本 PR 不合并、不部署到生产；需要先有独立测试数据库和 GCS 存储的集成测试结果。Brand Profile 仍是 `draft`，与内容渲染/发布还没有打通。


## M0-3b 多门店隔离切片（2026-11-21）

- 根据 PoStory 代运营业务，将尚未合并／尚未部署的初版数据库设计升级为 `ContentBrandShop` → `ContentBrandProfile` 和 `ContentBrandAsset`。每个登录账号可管理多家寿司店，但不允许越权打开他人门店。
- `GET/POST /api/content-engine/shops`：列表按账号归属筛选，创建仅支持寿司行业，限制每账号最多 40 家（初步滥用保护）。
- `GET /api/content-engine/brand?shopId=...` 和 `PUT /api/content-engine/brand` 中的 `shopId` 必须对应当前登录用户拥有的门店。草稿乐观锁依门店独立计算版本。
- 上传原图时必须包含 `shopId`；资产记录与私有 GCS 对象使用该门店 ID；读取图片通过资产所属门店关联到账号鉴权，不能只检查是否登录。
- `/for/sushi/brand` 可以选择已有门店、创建新门店，进入独立资料预览。门店切换清理未保存的本地图片对象 URL，不会把上家门店草稿继续提交给下家。
- **仅在未合并的开发分支上替换原迁移**。本迁移从未被应用到生产数据库；若另有环境已经试用了旧迁移，不能盲目直接运行修改后的同名迁移，需要人工核对 migration history。
- 当前只支持账号所有权，不支持代理商分配成员、邀请门店负责人或多人审核。真正的代理商协作模型需单独评审。
- 仍待在隔离测试环境中执行迁移，使用两个不同账号和同账号多门店分别做跨租户访问测试；自动构建成功不等于实际数据库、GCS、浏览器联调通过。
- 仍需图片解码/像素上限、上传频率限制、文件生命周期与孤儿文件清理机制、历史版本审计，以及正式品牌审核入口。

建议下一阶段工作：数据库/GCS 联调与真实权限验证 → 品牌确认及审计记录 → 后续模板 Renderer 读取已确认 Profile。
